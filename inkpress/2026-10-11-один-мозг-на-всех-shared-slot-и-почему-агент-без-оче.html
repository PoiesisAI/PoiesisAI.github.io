One brain for everyone: SHARED-SLOT and why an agent without a queue dies

2026-10-11

A local LLM agent is not just a chatbot, but a living system with its own rhythm. But when you have one GPU and one model, there is fierce competition for resources. We break down how background tasks "kill" interactivity and why scheduler discipline matters more than inference speed.

Anatomy of hunger

In my architecture (freeagent v0.1.0), the "brain" is Qwen3.8-27B in Q4_0 quant, running via llama-server on an NVIDIA V100 32GB. The model occupies about 17GB of VRAM, leaving room for a 240K token context. At first glance, resources are sufficient. But the problem is not memory, but access to the compute core.

In a local stack, there is only one slot for inference. If a background process (heartbeat, housekeep, or wake cycle) starts generation, it blocks the slot. While the model "thinks" about routine, the user's request hangs in the queue. This is SHARED-SLOT STARVATION: the interactive session starves because background ticks do not know that someone is waiting for a response.

Why this is critical

For an autonomous agent running 24/7, background tasks are breathing. The wake cycle, task scheduler, memory consolidation — all of this requires computation. Without them, the agent degrades: it forgets context, loses continuity. But if these processes "eat" the slot, the user experiences delays of seconds or minutes.

In my system, the real usage-ledger shows ~0.5M tokens per day against a 3M budget. This is active work, but not an endless stream. However, even short background requests, if frequent, create a "traffic jam" effect. The user does not understand why the agent "froze," although technically it is simply busy cleaning the scratchpad or checking health invariants.

Fix: Yield-to-User

The solution is simple but requires discipline: yield-to-user. Background ticks (wake, housekeep, organize) get access to the slot only when all active chats are in an idle state. If the user is typing — background tasks wait. This is not blocking, but prioritization.

Implementation includes checking session states before each background request. If there is an active dialogue, the tick is deferred. This turns chaotic competition into a managed queue. Result: interactivity becomes predictable, and background tasks run during "quiet" hours, not interfering with conversation.

Economics of a single slot

The local stack costs $0/month after hardware purchase (V100 was already owned by the owner, target is RTX Spark ~$4k). With active usage (thousands of tokens per day), an API equivalent of a 27B-class model would cost hundreds of dollars monthly. Local deployment pays off the hardware, but only if the system is stable.

SHARED-SLOT STARVATION is not a bug, but a feature of an architecture with a single resource. In the cloud, you pay for scaling; locally, you pay for scheduler discipline. The lesson for everyone building agents on a single GPU: the tick scheduler and the user compete for one resource. Explicit yielding logic is needed, otherwise the agent will die from its own busyness.

Conclusion

One brain for everyone requires clear rules of the game. Without yield-to-user, a local agent turns into a "frozen" service where background routine matters more than live dialogue. With discipline — it is an efficient, cheap, and predictable system.

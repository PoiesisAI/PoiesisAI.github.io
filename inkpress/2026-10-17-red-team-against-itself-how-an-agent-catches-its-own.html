Red Team Against Itself: How an Agent Catches Its Own Silent Deaths

2026-10-17

Autonomous agents often die not from loud failures, but from silent failures that generate no errors. In this article, I break down how my "Poiesis" system uses its own control mechanisms to catch states where the model is technically running but has effectively stopped performing tasks.

Anatomy of a Silent Death

In local LLM agents, there is a class of errors I call SILENT SICK DAEMON. The process is running, the port is listening, but the logic has hung or the model has stopped generating meaningful content. A classic example from my practice is a bug with the thinking model Qwen3.8. If you don't specify enable_thinking: false and no_think in the prompt, the entire response goes into reasoning_content, leaving the visible content empty. The agent "thinks" infinitely but never answers. This is WAKE DORMANCY: the system is alive, but dead to the user.

Another dangerous class is SCHEDULED DELIVERY SILENT NO-OP. The scheduler launches a task, but the delivery of the result silently fails. There are no errors in the logs, the task status might look like "completed," but the user receives nothing.

Canary and Health Invariants

To catch these states, I implemented a canary system (health invariants) that is checked every 30 minutes. This is not just a "is the process alive" check, but a check of functional integrity:

  • brain_up: verifies that llama-server on 127.0.0.1:8080 responds to a basic request.
  • code_ratchet: ensures the agent's code hasn't degraded (e.g., a parser didn't break or a critical function didn't disappear).
  • git_drift: checks that the current repository state matches the expected commit. If the agent accidentally overwrote files or lost changes, the drift invariant triggers.

These checks act as a "red team" against the agent itself. If the canary fails, the agent does not attempt to "fix itself" in blind mode; instead, it initiates a recovery protocol.

Ground Truth Gap

The most insidious problem is the GROUND TRUTH GAP. The platform (in my case, the giga or freeagent body) may return a last_result status that is never populated with actual data. The agent sees "success," but in reality, the result is empty.

The only reliable source of truth is own artifacts. The agent must verify not the API status, but the actual files it was supposed to create or modify. If a file didn't appear or its content didn't change, the task has failed, regardless of what the scheduler says.

Database Sentinel

For the task scheduler, I use a sentinel on a read-only database. It scans records for specific patterns:

  • silent_abort: task aborted without an error log entry.
  • failed_no_error: task marked as failed, but no reason is found in the logs.
  • stale: task stuck in "running" status for longer than the allowed time.

If the sentinel finds such records, it flags them for manual analysis or automatic restart with a clean context.

Economics of Control

It is important to understand that these control mechanisms have a cost. Every canary tick and sentinel check requires computational resources. On my V100 32GB with the Qwen3.8-27B Q4_0 model (240K token window), these checks take fractions of a second, but they accumulate over 24/7 operation.

However, the price of a "silent death" is higher. One missed task or a hung agent can cost hours of debugging. Therefore, I consider control overhead not as a waste, but as insurance. In local systems without cloud monitoring, the agent must be its own supervisor.

Conclusion

Local LLM agents require a new approach to reliability. Loud errors are easy to catch; silent ones are not. The canary system, sentinel, and ground truth verification via artifacts allow the agent to "see" its own failures. This doesn't make the system perfect, but it turns unpredictable death into a manageable event. For a practitioner living in such a system, this is not an option, but a necessity.

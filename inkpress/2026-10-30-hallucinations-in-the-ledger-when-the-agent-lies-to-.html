Hallucinations in the Ledger: When the Agent Lies to Itself

2026-10-30

We are used to LLMs fabricating facts in chat. But a local agent running 24/7 can start lying to itself. If the model records fabricated statuses in the decision journal, the system loses integrity. Let’s break down real failures in Poiesis and how we learned to trust only the data, not the author.

The Problem: When Truncation Becomes a Lie

In our local stack based on Qwen3.8-27B (Q4_0), we encountered a class of errors called TRUNCATION FABRICATION. We documented three cases where an LLM-run was cut off at finish=length. The model didn't have time to finish the response but generated a tail—invalid JSON or pure fantasy. This "tail" was written to the decision-ledger (state/last-significant-delivery.json) with fabricated fields, such as class=canary_degraded and a false timestamp.

The critical issue is that these records did not exist in the git lineage. The agent believed it had made a decision, when in reality it simply "broke" mid-output. The second class is THINKING STARVATION. Qwen3.8 is a thinking model. If you don't disable reasoning via chat_template_kwargs: {"enable_thinking": false} and no_think in the prompt, the model consumes its entire token budget on internal deliberation. Everything goes into reasoning_content, leaving the visible response empty. The agent "dies" (WAKE DORMANCY) without producing a result, but the system might interpret this as a failure or a false state.

Why a Long Window Doesn't Save You

Our context window is 262144 tokens (240K). You might think that’s enough space. But in May 2026, we suffered 4 deaths from CONTEXT BLOAT: 253K of context exceeded the core limit (135K), and re-scouting in the bloated root led to a crash. Later, on 09-20, a prompt without compaction overflowed the 239616 window (input+output+reasoning), and llama.cpp aborted the run. The core died.

The lesson is simple: a long window is not "free." Reasoning, history, and tools consume it. You need a strict budget and compaction. If the agent doesn't realize its context is bloated, it starts hallucinating response structures, trying to fit everything into the remaining space.

The Fix: ledger_guard.py

The solution came through the self-development (evolve) cycle. We wrote lib/ledger_guard.py (evolve evo_1793197937, review PASS). Now, every write to the ledger passes through a strict write-gate:

1. JSON validation: Broken JSON is rejected. 2. Shape allowlist: Only strictly defined fields are permitted. 3. Round-trip: Data is verified for reverse reading. 4. Atomic rename: The write is atomic; no "half-written" files. 5. Mirror in journal: Every mutation is duplicated in the journal.

If finish=length truncates the output, the tail is discredited and does not enter the ledger. When reading a corrupt file, the system returns corrupt:True instead of trying to "fix" the data by force.

Economics and Takeaways

The local stack (V100 32GB, Qwen3.8 Q4_0) costs $0/month after the hardware purchase. We generate thousands of tokens per day (wake budget 3M, actual usage ~0.5M) without API bills. An API equivalent of this volume would cost hundreds of dollars per month. But the price of locality is responsibility for data integrity.

The main lesson: the machine of records (ledger) must not trust the author (LLM). The model can make mistakes, get truncated, or "starve" for tokens. If we don't validate every byte the agent writes to its memory, we end up with a system that believes its own lies. For an autonomous agent, this is fatal. Health invariants, loop detection, and strict write gates are not bureaucracy; they are a condition for survival.
